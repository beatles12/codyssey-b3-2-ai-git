## 1. 미션 한 줄 요약

`git status` / `git diff` 결과를 읽어 AI API에 보내고, 돌아온 글을 **커밋 메시지**와
**PR 제목·본문 초안**으로 다듬어 터미널에 출력하는 **Python CLI 도구**를 만든다.
핵심은 API 호출 자체가 아니라 **"어떤 입력(프롬프트)을 주고, 받은 결과를 어떻게 검증하느냐"** 이다.

### 2-4. 이 실습의 선택 (공식 필수 아님, 권장)

| 항목 | 이유 |
|---|---|
| `--dry-run` 옵션 | AI 를 부르지 않고 "보낼 프롬프트"를 먼저 확인 → 비용 0원으로 민감정보·길이 점검 |

## 4. 원리 정리

### 4-1. Git 변경 사항 수집 원리

```
[Python]  subprocess.run(['git', 'status', '--porcelain'], ...)
              │  git 프로그램을 "다른 프로세스"로 실행하고
              ▼  그 출력(stdout)을 문자열로 받는다
[문자열]  " M todo_app/app.py\nA  todo_app/search.py\n"
              │  줄 단위로 나누고, 앞 2글자(상태 코드)와 경로를 분리
              ▼
[목록]    [{'code': 'M', 'path': 'todo_app/app.py'}, {'code': 'A', ...}]
```

- `git status --porcelain` : **무엇이** 바뀌었나 (파일 목록, 기계가 읽기 쉬운 고정 형식)
- `git diff --cached` : `git add` 한(staged) 변경의 **내용**
- `git diff` : 아직 `git add` 안 한(unstaged) 변경의 **내용**
- 새 파일(`??`, untracked)은 status 에는 보이지만 diff 에는 나오지 않는다
- 저장소 확인과 브랜치 이름도 `git status` (`--porcelain --branch` 의 첫 줄 `## 브랜치`)로 얻을 수 있다 → 공식 제약 "수집은 status·diff 범위"를 엄격하게 지키는 방법
- `git log` 는 **이미 커밋된 과거 기록** → 이번 미션의 입력이 아님 (교재 'Git diff 와 Git log 차이')

### 4-2. AI API 연동 원리 (REST API)

```
API Key (환경변수) ─┐
프롬프트(문자열) ───┼─► 요청 만들기 ─► HTTP POST (JSON) ─► AI 서버
옵션(model 등) ────┘   headers+body                          │
                                                             ▼
터미널 출력 ◄─ 다듬기 ◄─ 글자 꺼내기 ◄─ JSON 응답 ◄──────────┘
```

| 단계 | 내용 | 표준 라이브러리 |
|---|---|---|
| 키 읽기 | `os.environ` 에서 `AI_API_KEY` | `os` |
| 요청 머리 | 인증 헤더 + `content-type: application/json` | — |
| 요청 본문 | `{"model", "max_tokens", "temperature", "messages": [{"role": "user", "content": 프롬프트}]}` | `json` |
| 보내기 | POST, timeout 지정 | `urllib.request` |
| 오류 | HTTP 상태 코드(401/400/429/5xx), 네트워크 오류, 시간 초과, JSON 아님 | `urllib.error` |
| 응답 | 제공자마다 글자 위치가 다름 (anthropic: `content[]` 중 `type == "text"`, openai: `choices[0].message.content`) | `json` |

**파라미터의 영향 (공식 과제 목표 2, 체크리스트 항목 3)**

| 파라미터 | 낮추면 | 높이면 | 이 실습 기본값 |
|---|---|---|---|
| `temperature` | 매번 비슷하고 보수적인 표현 (재현성↑) | 표현이 다양해지고 예측하기 어려움 | 0.3 |
| `max_tokens` | 출력이 짧아지고, 너무 낮으면 **중간에 잘림** (`stop_reason: max_tokens`) | 길게 쓸 여유. 실제 사용량만큼 과금되지만 상한이 커지면 최악의 비용도 커짐 | 1024 |

> ⚠️ **확인된 주의점** — 최신 모델 중에는 `temperature` 를 거부하거나(HTTP 400) 기본값만 허용하는 모델이 있습니다.
> 예: Anthropic 의 Claude 4.7 이후 모델은 temperature 를 바꿀 수 없고(기본값이 아닌 값, 일부 모델은 값과 상관없이 HTTP 400), API 버전 `2026-10-21` 에서는 모든 모델이 temperature 를 거부합니다.
> 그래서 이 실습은 `anthropic-version: 2023-06-01` + temperature 를 받는 모델(`claude-haiku-4-5`)을 기본값으로 두었습니다.
> 체크리스트 항목 1의 "temperature **또는** max-tokens 변경 시 차이 재현"은 **max-tokens 만으로도** 확인할 수 있습니다.
> 기본값만 받는 모델(예: Claude Haiku 5.5, Sonnet 5.5)은 `--temperature 1.0` 으로 실행하면 됩니다.
> OpenAI 의 추론 계열 모델은 temperature 를 바꿀 수 없고, `max_tokens` 대신 `max_completion_tokens` 를 요구합니다. (연습 테스트는 openai 형식에서 두 이름을 모두 인정합니다.)
> 실제로 쓸 제공자·모델이 정해지면 그 제공자의 공식 문서를 꼭 다시 확인하세요.

### 4-3. 커밋 메시지·PR 설명 생성 과정

| 순서 | commit | pr |
|---|---|---|
| 1 | 저장소 확인 | 저장소 확인 + **현재 브랜치** |
| 2 | 변경 파일 목록 (없으면 종료) | 같음 |
| 3 | diff 수집 → 줄 수 로그 | 같음 |
| 4 | `--safe-mode` 면 마스킹·전송 제한 | 같음 |
| 5 | **커밋용** 프롬프트 (제목 50/72자, 불릿 1~2개) | **PR용** 프롬프트 (제목 80자, Why/What/How to Test) |
| 6 | AI 호출 1회 (호출 횟수 로그) | 같음 |
| 7 | 제목/본문 분리 → 72자 규칙 적용 → 검증 | 제목/본문 분리 → 80자 규칙 + 섹션·불릿 검증 |
| 8 | `--- Commit Message ---` 구획 출력 | `--- PR Title ---` / `--- PR Body ---` 구획 출력 |

**재생성 vs 후처리 (체크리스트 항목 3 마지막 질문)**

| | 후처리 | 재생성 |
|---|---|---|
| 방법 | 프로그램이 직접 자르기·다듬기 | 규칙 위반 시 AI 에 한 번 더 요청 |
| 비용 | 추가 비용 없음 | 호출 최대 2회 (공식 권장 상한) |
| 장점 | 빠르고 결과가 확실히 규칙을 지킴 | 자연스러운 문장 유지 |
| 단점 | 잘린 제목이 어색할 수 있음 | 두 번째도 어길 수 있음 → 결국 후처리 필요 |

### 4-4. 입력값 검사·오류 처리

| 상황 | 어디서 잡나 | 출력 예 | 종료 코드(권장) | AI 호출 |
|---|---|---|---|---|
| 하위 명령 없음 / 숫자 아님 | argparse | usage + error | 2 | ✗ |
| temperature·max_tokens 범위 밖, 빈 model | `validate_options()` | `[ERROR] temperature 는 0.0 ~ 1.0 ...` | 2 | ✗ |
| Git 저장소가 아님 | `is_git_repository()` | `[ERROR] Git 저장소가 아닙니다 ...` | 1 | ✗ |
| 변경 사항 없음 | `get_changed_files()` | `[INFO] 변경 사항이 없습니다 ...` | 0 | ✗ |
| API Key 없음 | `get_api_key()` | `[ERROR] AI_API_KEY 환경변수가 설정되지 않았습니다.` | 1 | ✗ |
| 인증 실패 (401) | `send_http_request()` | `[ERROR] AI API 요청 실패 (HTTP 401): ...` | 1 | 1회 |
| 잘못된 요청 (400, 예: 모델이 temperature 거부) | 같음 | `(HTTP 400): ...` | 1 | 1회 |
| 요청 과다 (429) / 서버 오류 (5xx) | 같음 | `(HTTP 429): ...` | 1 | 1회 |
| 네트워크 오류 / 시간 초과 | 같음 | `[ERROR] 네트워크 오류 ...` | 1 | 1회 |
| 응답 모양이 다름 / 빈 글 | `extract_text()` | `[ERROR] 응답 형식이 예상과 다릅니다 ...` | 1 | 1회 |
| 결과가 길이·형식 규칙 위반 | `validate_*()` | `[WARN] ...` 또는 자동 수정 | 0 | 1~2회 |

**원칙** — 돈이 드는 AI 호출 **전에** 검사할 수 있는 것은 모두 먼저 검사한다. 오류 메시지에는 **원인과 해결 방법**을 넣고, **API Key 값은 절대 넣지 않는다.**

### 4-5. 보안·API 비용 관리

| 위험 | 대응 | 이 실습에서 |
|---|---|---|
| 키가 코드·커밋에 섞임 | 환경변수만 사용, `.env` 는 `.gitignore` | `tests/base/test_05_security.py` 가 키 모양 문자열을 계속 감시 |
| diff 에 키·개인정보 | `--safe-mode` 마스킹 (A) | Step 3 `mask_sensitive()` |
| diff 가 너무 큼 (비용↑) | 전송 제한 (B) 10파일·200줄 | Step 3 `limit_diff()` (선택) |
| 반복 실행으로 비용 폭주 | 1회 실행 = 1회 호출, 호출 횟수 로그, `max_tokens` 상한 4096 | Step 1, 7 |
| 보내기 전 확인 불가 | `--dry-run` 으로 프롬프트 미리 보기 | Step 7 (선택) |
| AI 결과를 그대로 사용 | 사람이 검토 후 적용 (README 에 명시) | Step 8 |
| 실습 중 실수로 실제 호출 | 테스트·데모가 네트워크를 차단 | `tests/helpers.py`, `learning_kit/demo.py` |

### 4-6. 자동 테스트 방법

| 종류 | 위치 | 지금 상태 | 실행 |
|---|---|---|---|
| 기본 환경 테스트 | `tests/base/` | **모두 통과해야 함** | `python -m learning_kit.practice base` |
| 단계별 연습 테스트 | `tests/practice/test_stepN_*.py` | 구현 전에는 `[TODO]` | `python -m learning_kit.practice N` |
| 표준 방식 | 위 둘 다 | — | `python -m unittest discover -s tests/base -t .` |

- 실제 AI API 대신 **가짜 통신(`FakeTransport`)** 을 넘겨 요청 내용·호출 횟수·오류 처리를 확인합니다.
- `urlopen` 자체를 가짜로 바꿔 HTTP 401·네트워크 오류·시간 초과를 흉내 냅니다.
- 테스트마다 임시 폴더에 **진짜 Git 저장소**를 만들어 `git status`/`git diff` 를 확인합니다.
- 실제 API 확인은 Step 8 에서 **사람이 직접 1~2회만** 합니다. (자동 테스트에 넣지 않음 → 비용·키 노출 방지)

## 6. 공식 자료가 정하지 않은 부분 — 이 실습의 선택

| 질문 | 공식 자료 | 이 실습의 선택 | 바꿔도 되나 |
|---|---|---|---|
| 어떤 AI 제공자? | 정하지 않음 ("AI API") | anthropic / openai 두 형식 지원, 기본 anthropic | ✅ `config.py` |
| 환경변수 이름? | 예시: `AI_API_KEY` | `AI_API_KEY` | 권장하지 않음 (테스트가 확인) |
| 파일 구조? | 정하지 않음 | `ai_gitgen/` 6개 모듈 + `main.py` | ⚠️ 함수 이름을 바꾸면 테스트도 고쳐야 함 |
| staged / unstaged? | "git diff 결과" | 둘 다 포함 (`--cached` + 기본) | ✅ 이유를 설명할 수 있으면 |
| 새 파일(untracked)? | 정하지 않음 | status 에는 포함, diff 에는 없음 → 파일 이름만 전달 | ✅ |
| 재생성 vs 후처리 | 택1 | 테스트는 둘 다 허용 (최종 제목 길이와 호출 ≤ 2회만 확인) | ✅ |
| 종료 코드 | 정하지 않음 | 정상·변경 없음 0, 오류 1, 옵션 오류 2 | ✅ (테스트는 0 / 0이 아님만 확인) |
| 출력 헤더 단어 | 결과 예시는 "참고용" | 공식 예시와 같은 `--- Commit Message ---`, `--- PR Title ---`, `--- PR Body ---` 를 테스트가 찾음 | ⚠️ 바꾸면 Step 6·7 테스트도 수정 |
| PR 에 현재 브랜치 표시 | 공식 `pr` 결과 예시에 있음 | 필수 (작업 맥락으로 프롬프트에도 넣음) | ✅ |
| 외부 패키지 | 정하지 않음 | 표준 라이브러리만 (`urllib`) | 가능하지만 테스트가 `urllib.request.urlopen` 을 가짜로 바꾸므로 Step 5 테스트를 고쳐야 함 |

### 7-2. 공식 미션과 충돌하는지

충돌하는 규칙은 없습니다. 함께 지키려면 다음처럼 해석합니다.

| 가이드라인 | 공식 미션 | 함께 지키는 방법 |
|---|---|---|
| 1절 "불필요한 기능 추가 금지" | 필수 기능 목록 | 공식에 없는 것(`--dry-run`, 다른 제공자 형식, 전송 제한 B 등)은 **선택 테스트**로만 둠 |
| 5절 "공통 예외는 진입점 데코레이터" | "API 호출 실패 시 오류 원인 포함 메시지", "키 없으면 오류 후 종료" | 하위 계층이 원인을 담은 예외를 raise → 데코레이터가 `[ERROR]` + 원인 + 힌트 출력, 0 이 아닌 종료 코드 |
| 5절 "데이터 오류는 사전 검증" | "변경 사항이 없으면 메시지 후 종료" | 변경 없음·옵션 범위 오류는 예외가 아니라 검사 결과로 처리 (각각 종료 0 / 2) |
| 2절 "긴 설명은 docs 로" | README 필수 내용 | 사용법은 README(제출물), 설계·명세는 `docs/` 에 나눠 둠 |
| 7절 docs 문서 | 결과물은 코드·리포지토리·README | docs 는 추가 문서이므로 제출 기준과 충돌하지 않음 |

### 7-3. 학습 지원 코드의 예외

- `learning_kit/`·`tests/` 의 **모듈 설명**은 `python -m ...` 실행 방법·테스트 범위를 알려 주는 안내라서 여러 줄로 유지했습니다. 함수 설명은 한 줄입니다.
- 학습 도구의 국소 `try/except` (데모가 TODO·오류를 만나도 다음 항목으로 넘어가기, 테스트 파일을 못 불러올 때 안내 등)는 학습 도구의 목적상 필요해서 유지했습니다.
- 줄 길이는 PEP 8 의 79자를 그대로 씁니다 (가이드라인에 별도 기준 없음).
